Stage 01

Parse the path.

Users paste any of three things: a raw d attribute value (M10,10 L100,10 …), a full <path d="…"> tag, or a complete <svg> document. We need to dig the d string out of whatever they gave us — everything downstream needs that one string.

(click extract)

Then we stash that d on a hidden inline <path> — the browser's SVG engine will do the heavy lifting in the next stage with getTotalLength() and getPointAtLength().

function extractD(text) {
  text = text.trim();
  // 1) anything containing d="…"
  const m = text.match(/\bd\s*=\s*"([^"]+)"/);
  if (m) return m[1];
  // 2) starts with M/m → assume it's a raw d
  if (/^[Mm]/.test(text)) return text;
  throw new Error("No path d=… found in input.");
}
Stage 02

Sample points along the path.

Now we ask the browser for the path's total length, then walk it at N evenly-spaced positions, getting an {x, y} for each. The number of samples is the only knob that decides curve fidelity — too few and Bézier arcs become polygons; too many and the bake is slow with no visible gain.

We also pick a span here: typically just the first half of the path, so the cycling band has somewhere to "go" without a visible seam where the band wraps back on itself.

Walk the path
// Stash the d on a hidden <path> so we can ask the SVG engine
// for arc-length parametrization.
const svg = document.createElementNS(NS, 'svg');
const p   = document.createElementNS(NS, 'path');
p.setAttribute('d', d);
svg.appendChild(p); document.body.appendChild(svg);

const total = p.getTotalLength();
const pts   = new Array(N + 1);
for (let i = 0; i <= N; i++) {
  const t = (i / N) * total * 0.5;   // first half
  const q = p.getPointAtLength(t);
  pts[i] = { x: q.x, y: q.y };
}
Stage 03

Stroke 254 colored segments → index canvas.

Here's the trick. We split the sample list into N = 254 consecutive segments and stroke each one with a unique R-channel value: segment i gets rgb(i+1, 0, 0). The stroke is fat and round-capped, so adjacent segments overlap and form a continuous fill. The red channel of the resulting bitmap is our per-pixel index buffer — read straight off the canvas.

Stroking line segments would polygonize curves, so each "segment" actually walks a few sub-segments along the path before changing index. That keeps Béziers smooth while preserving the 1..254 encoding.

Index encoding
const idx = document.createElement('canvas');
idx.width = W; idx.height = H;
const ictx = idx.getContext('2d');
ictx.lineWidth = STROKE_W;
ictx.lineCap   = 'round';
ictx.lineJoin  = 'round';

for (let i = 0; i < 254; i++) {
  ictx.strokeStyle = `rgb(${i+1}, 0, 0)`;
  ictx.beginPath();
  const base = i * SUBSEG;
  ictx.moveTo(pts[base].x, pts[base].y);
  for (let j = 1; j <= SUBSEG; j++)
    ictx.lineTo(pts[base+j].x, pts[base+j].y);
  ictx.stroke();
}
// idx canvas: red channel now encodes "where along the path"
Stage 04

Mask & combine into a Uint8Array.

The index canvas has soft anti-aliased edges where indices fade to zero, which would flicker badly under cycling. So we paint a second canvas — same geometry, same path, but a single solid stroke — and use its alpha channel as the binary "is this pixel inside the shape?" decision. We then walk every pixel once and pack the result into a flat Uint8Array: 0 means transparent, 1..254 means "this index in the palette".

One typed array, one byte per pixel. That's the entire baked artifact; everything else can be thrown away.

The bake
// Bake into one flat byte-per-pixel buffer.
const indices = new Uint8Array(W * H);
for (let i = 0; i < W * H; i++) {
  if (mask[i*4+3] < 200) { indices[i] = 0; continue; }
  let v = idxData[i*4];
  if (v < 1)   v = 1;
  if (v > 254) v = 254;
  indices[i] = v;
}
Stage 05

Build a palette LUT.

A palette is a length-256 lookup table of 32-bit RGBA values. Slot 0 is always transparent. Slots 1..255 hold a smooth color ramp built by interpolating between a handful of stops. Different palettes — sodium, plasma, rainbow, cyan — are just different stop lists. The whole bake stays the same; only this 1KB lookup changes.

Pick a ramp
const palette = new Uint32Array(256);
palette[0] = 0; // transparent
for (let i = 0; i < 255; i++) {
  const [r, g, b] = ramp[i];           // from your stops
  palette[i + 1] = (255 << 24) | (b << 16) | (g << 8) | r;
}
Stage 06

The render loop.

This is the punchline. Every frame:

  1. Bump offset by speed × dt.
  2. Rebuild the 256-entry palette so slot i+1 reads from ramp[(i+offset) mod 255]. (1KB worth of work.)
  3. Walk the indices buffer once, writing data32[i] = palette[indices[i]].
  4. putImageData.

That's it. No SVG, no drawPath, no compositing. The geometry was baked once. Animation is just "shift a 1KB lookup, then do one tight pass over a typed array." A 1500×600 logo runs at 60fps with cycles to spare.

The technique itself isn't new — palette cycling carried entire eras of 8-bit and 16-bit graphics, and Mark Ferrari's Living Worlds pieces (the rain-on-a-village, the lava flow) are the canonical demonstration of how much motion you can get out of one static image and a rotating LUT. We're just running it over a freshly baked SVG path instead of a hand-drawn 320×200 scene.

Live
function frame(now) {
  const dt = (now - last) / 1000; last = now;
  offset += speed * dt;

  // rotate the palette (cheap — 1KB)
  for (let i = 0; i < 255; i++) {
    const k = ((offset - i) % 255 + 255) % 255;
    palette[i + 1] = ramp32[k | 0];
  }

  // the hot loop — one lookup per pixel
  for (let i = 0; i < n; i++) data32[i] = palette[indices[i]];
  ctx.putImageData(image, 0, 0);

  requestAnimationFrame(frame);
}

Each frame, palette index i+1 reads ramp position (offset - i) mod 255. Adjacent palette indices read adjacent ramp positions; as offset grows, every pixel sees the next color in the ramp one tick later than its neighbour. That's the entire animation.

Stage 07

Custom palettes from stops.

The presets are seven hand-rolled lookup tables, but the format underneath is just a list of color stops at positions in [0, 1]. Linear-interpolate between adjacent stops and you have any 255-entry ramp: sodium-glow becomes plasma becomes a personal one with three teal stops crammed into the middle.

stops re-flow the ramp on the fly 
function buildRamp(stops) {
  const sorted = stops.slice().sort((a,b) => a.t - b.t);
  const out = new Array(255);
  for (let i = 0; i < 255; i++) {
    const t = i / 254;
    // find the two stops bracketing t
    let a = sorted[0], b = sorted[sorted.length - 1];
    for (let k = 0; k < sorted.length - 1; k++) {
      if (t >= sorted[k].t && t <= sorted[k+1].t) {
        a = sorted[k]; b = sorted[k+1]; break;
      }
    }
    const u = (t - a.t) / (b.t - a.t || 1);
    out[i] = [
      Math.round(a.color[0] + (b.color[0] - a.color[0]) * u),
      Math.round(a.color[1] + (b.color[1] - a.color[1]) * u),
      Math.round(a.color[2] + (b.color[2] - a.color[2]) * u),
    ];
  }
  return out;
}

The stop list is the only per-palette state we ever ship — at most a few dozen {t, color} pairs. Everything downstream operates on the 255-entry ramp it produces.

Stage 08

Smooth palette transitions.

Switching from one palette to another mid-cycle is jarring if you do it as a hard cut: every position on the path snaps to a new color in the same frame, even when the palettes are similar. The trick is to feed the new palette in at one position — palette[1], the head of the cycle — and let the cycle's existing motion carry it along the path.

Each frame we split the read by tape position s = offset − i. Cells past the boundary read from p2; cells behind still read from p1. As offset advances, the boundary moves through the ramp one slot at a time. After 254 ticks every visible position has been swept — the new palette is fully in, and we promote it to base.

Drag the slider — watch the boundary sweep
0/254 — fully p1 
// Inside _writePalette: split each palette index by tape position.
for (let i = 0; i < 255; i++) {
  const s = offset - i;
  let ramp, pos;
  if (nextPalette && s >= nextStartOff) {
    ramp = nextPalette;                      // swept — read p2
    pos  = (s - nextStartOff) % 255;
  } else {
    ramp = basePalette;                      // not swept — p1
    pos  = (s - baseStartOff) % 255;
  }
  palette[i + 1] = sample(ramp, pos);
}

// Promote when every visible position has been swept.
if (nextPalette && offset - nextStartOff >= 254) {
  basePalette = nextPalette;
  baseStartOff = nextStartOff;
  nextPalette = null;
}

The watcher above schedules nextStartOff = baseStartOff + cycles × 255 so the swap lands exactly when palette[1] would have wrapped from p1[254] back to p1[0] — instead, palette[1] reads p2[0], and p2[1] next tick, and so on. No tween, no wall clock, just the cycle's natural motion doing the work.

Stage 09

Self-describing PNG.

The finished logo wants four things to be portable: the indexed buffer (the bake), the palette stops (so you can re-render), the editable bezier anchors (so you can come back and tweak), and the cycle config (speed, mode, ordering). All of that fits comfortably in a few KB of JSON.

Rather than ship a JSON sidecar, we put it inside the PNG itself. The PNG body is an RGBA snapshot of the cycling output — so the file shows up in Finder, GitHub diffs, og:image previews, anywhere — and an iTXt chunk keyed pshift carries the metadata. Save it as *.pshift.png; the runtime reads the chunk, the rest of the world sees a normal PNG.

PNG layout
PNG signature  — 8 bytes
IHDR           — width × height, color type 6 (RGBA)
IDAT*          — compressed RGBA preview pixels
iTXt           — keyword "pshift", text = JSON {
                 version, width, height,
                 indices  (base64 Uint8Array, 1 byte/pixel),
                 anchors  (bezier control points, for round-trip),
                 palettes (array of {name, stops, speed, cycles}),
                 activeIdx, playMode, strokeWidth, scale, padding
               }
IEND           — end of stream

The loader pulls the PNG, decodes the indices straight out of the iTXt chunk (no rebake), pipes the palette stops through buildRamp, and runs the playlist scheduler from Stage 08 if there's more than one palette. The static preview the file ships with is rendered from palette[0] at offset = 0 — so what you see in Finder matches the first frame the engine paints.

The drawing tool feeds raw pointer events through Steve Ruiz's perfect-freehand for the visible stroke rendering, simplifies the trail with Ramer–Douglas–Peucker, and converts each polyline run into cubic Béziers via Catmull–Rom — small classics, all of them. Everything else above is hand-rolled against bare Canvas and SVG APIs.
